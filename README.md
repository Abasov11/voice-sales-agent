# voice-sales-agent — голосовой ИИ-агент исходящих звонков

> **Портфолио-кейс.** Витрина инженерного решения: архитектура, ключевые приёмы и
> подобранные фрагменты кода. Не рабочая сборка — ключи, вебхуки, база лидов и
> сведения о заказчике сюда не входят. Бренд и PII обезличены.

## Задача

Детская спортивная школа собирает заявки/лиды (сайт, реклама, старая база), но
живые менеджеры физически не успевают обзвонить всех — часть лидов остывает
до первого контакта. Нужен голосовой ИИ-агент, который сам обзванивает базу,
ведёт диалог по-русски (представляется, уточняет интерес, возраст ребёнка,
район, отвечает на возражения), квалифицирует лида и доводит заинтересованных
до записи на пробную тренировку — без участия менеджера на этом этапе.

**Что делает система:** исходящий обзвон базы по телефонии → голосовой диалог
через LLM → при интересе — сообщение в WhatsApp и карточка в CRM → дашборд с
аналитикой звонков (включая звонки живых менеджеров отдела продаж) для
руководителя школы.

## Главный вызов — чтобы голосовой агент не звучал как бот

LLM хорошо ведёт диалог по содержанию, но на голосе регулярно "выдаёт себя"
конкретными паттернами: дежурный отклик в начале почти каждой реплики
("Понимаю вас, ..."), зачитывание уже известных от клиента фактов квитанцией
("Про район и возраст — ..."), несколько вопросов подряд в одной реплике —
по телефону это невозможно разобрать на слух, клиент теряет нить. Промпт
такие вещи "лечит" ненадёжно: конкретная жалоба на живом звонке фиксится,
через несколько диалогов паттерн выныривает снова в другой формулировке.

Решение на первом, серийном контуре (STT → LLM → TTS) — не бороться с этим
только промптом, а поставить детерминированный слой постобработки **после** LLM, который не
трогает содержание ответа, только конкретные, заранее описанные "робо-паттерны":

1. **Снятие дежурного зачина.** Если реплика начинается с одной из известных
   filler-фраз и дальше есть содержание — зачин срезается, регистр первой
   буквы восстанавливается. См. [`snippets/voice_naturalness_guardrails.py`](snippets/voice_naturalness_guardrails.py).
2. **Снятие эха уже известных фактов.** Модель получает в промпте факты,
   которые клиент уже назвал (чтобы не переспрашивать), но иногда зачитывает
   их перечнем в начале реплики — паттерн распознаётся и срезается.
3. **Один вопрос за ход.** Если в реплике 2+ вопросительных знака, оставляется
   текст по первый включительно — остальное прозвучит следующим ходом.
4. **Латентность первого хода — отдельно от контента.** Первая реплика после
   снятия трубки не идёт через LLM вообще: это самая заметная пауза звонка (в
   проекте её сократили с ~8.5с до ~1с) — приветствие детерминированное
   (шаблон + подстановка имени), а TTS кэшируется по контенту. См.
   [`snippets/tts_latency_cache.py`](snippets/tts_latency_cache.py).

Итог первого контура: промпт задаёт общий тон диалога, но конкретные проговорки, которые слышны
на записи как "бот", ловятся и правятся воспроизводимо — маленьким детерминированным
слоем, а не бесконечной подгонкой промпта под очередную жалобу.

## Переход на speech-to-speech

Серийный контур упирался в сумму задержек трёх провайдеров: пауза перед ответом
агента была около 3,4 с, на телефоне это слышно как «бот думает». Агент переведён
на speech-to-speech модель (OpenAI Realtime): речь клиента идёт в модель напрямую,
без отдельных STT и TTS, и пауза сократилась примерно до 800 мс.

Что пришлось решить по дороге:

- **Сценарий звонка тонкий, скрипт кампании — на бэкенде.** Параметры, которые
  телефонная платформа передаёт в сценарий, ограничены 200 символами, а скрипт
  кампании — полтора-два килобайта. Сценарий при старте звонка сам забирает с
  бэкенда инструкции, приветствие и голос по id лида, поэтому новая кампания
  запускается без правки кода.
- **Бэкенд не видит реплики вживую**, значит итог звонка считается после него:
  запись → транскрибация → классификация исхода и извлечение полей → CRM.
- **Мгновенный откат.** Старый серийный путь остался отдельным правилом
  маршрутизации звонков; переключение между путями — одна настройка, без деплоя.

## Ещё инженерные решения

- **Роли в транскрипте — из диаризации, а не догадкой модели.** Замер на боевых
  записях показал: когда модель сама размечала, кто говорит, она путала роли и
  дописывала клиенту слова, которых он не говорил, и лид получал неверную
  квалификацию. Теперь роли приходят из диаризации STT-провайдера, а сигналы
  квалификации настраиваются под каждую кампанию.
- **Разбор массового обзвона.** В одной кампании из 219 звонков 106 получили
  ложный исход «абонент молчал». Причина найдена и исправлена, повторная
  обработка старых записей вернула 5 потерянных горячих лидов.
- **Явная таксономия сбоев телефонии, а не общий retry.** Звонок может не
  состояться десятком разных способов (не взяли трубку, автоответчик, оператор
  заблокировал номер после серии звонков, плохое качество записи и т.д.) — в
  проекте это 13 классов сбоев с собственным root cause, детектом и recovery
  у каждого. Один и тот же ответ на все ("просто ретраим") либо спамит
  автоответчик, либо теряет лида. См.
  [`snippets/telephony_failure_classifier.py`](snippets/telephony_failure_classifier.py)
  и [`docs/architecture.md`](docs/architecture.md).
- **Каскад STT-провайдеров + роутинг LLM по стоимости.** В модуле аналитики
  звонков менеджеров транскрибация переключается на secondary-провайдера при
  сбое primary без падения пайплайна; LLM-оценка диалога роутится по
  длительности звонка — короткие несостоявшиеся разговоры (основная масса
  потока) идут через дешёвую модель, длинные продающие диалоги — через модель
  классом выше. См. [`snippets/stt_llm_fallback_routing.py`](snippets/stt_llm_fallback_routing.py).
- **Не выдумывать исход звонка.** Финальная классификация (заинтересован /
  не заинтересован / перезвонить) размечается по словам именно клиента, а не
  всего транскрипта — иначе агент, сам произносящий "запишу"/"адрес", ловит
  собственные слова как признак интереса. LLM-классификатор — приоритетный
  путь, при недоступности — детерминированный keyword-классификатор поверх тех
  же категорий, настраиваемых в дашборде.
- **Fallback без LLM/TTS не рвёт диалог.** Если провайдер недоступен —
  натуральный текстовый ответ по текущей стадии диалога вместо падения
  звонка; TTS-ошибка не блокирует ответ — реплика уходит текстом.
- **Ролевой дашборд аналитики.** 4 роли доступа (владелец / директор /
  руководитель продаж / менеджер) — менеджер видит только свои звонки и
  оценки, стоимость API видит только владелец.

## Архитектура

Подробнее, с диаграммами потока и таблицей recovery — [`docs/architecture.md`](docs/architecture.md).

```
CSV-база лидов → очередь дозвона → исходящий звонок (SIP-телефония)
                                          │
              сценарий звонка забирает скрипт кампании с бэкенда
                                          │
   сейчас:  речь клиента ⇄ speech-to-speech модель (OpenAI Realtime)
   раньше:  речь → STT → LLM-реплика → анти-робот guardrails → TTS (кэш)
                                          │
        после звонка: запись → STT с диаризацией → классификация исхода
                                          │
                interested → WhatsApp (Green API) + карточка в CRM (AlfaCRM)
                                          │
                                     PostgreSQL ← дашборд (4 роли)

Параллельно: звонки живых менеджеров → запись → каскад STT →
             LLM-оценка (роутинг по длительности) → отчёт в дашборде
```

## Стек

Python · FastAPI · PostgreSQL · SQLAlchemy · Alembic — телефония Voximplant
(SIP, сценарии звонка на JS) · OpenAI Realtime (speech-to-speech) · TTS с кэшем
по контенту (первый контур) · LLM (классификация исхода + оценка звонков
менеджеров) · STT с диаризацией и каскадом провайдеров · WhatsApp-канал (Green API) · CRM
(AlfaCRM REST, двусторонний sync) · серверный дашборд (FastAPI + Jinja2 +
Tailwind), ролевой доступ.

## Статус

Рабочая система в проде: голосовой агент обзванивает базу, ведёт диалог,
квалифицирует и передаёт заинтересованных лидов дальше по воронке; параллельно
работает аналитика звонков менеджеров и ролевой дашборд. Покрыта 545 автотестами
(pytest). Полная сборка,
вебхуки, база лидов и промпты заказчика в этот публичный кейс не входят.
